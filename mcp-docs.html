The CutLab MCP: your agent can edit, not just render

CutLab is a video editor that runs in the browser. Its MCP server lets an AI assistant you already use work on your projects directly: building timelines, grading, captioning, queueing renders, and rendering on its own machine. You connect your chat, never an API key. 100% of the engine is agent-callable — zero UI-only features: every edit the editor can make, from a trim to the full grade object, is exposed as a tool. Other editors count commands; CutLab exposes the whole engine.

Overview

The honest starting point: CutLab's rendering engine has always been deep. The project schema defines around 140 fields across five clip types, the grade object alone carries around 60 addressable parameters, and counting keyframes, effects and export options the renderer honours roughly 200 parameters and operations. For a long time an agent could reach almost none of it. The first MCP release exposed exactly seven tools, and not one of them could edit anything: they listed projects and ran the render lane.

The Agent Control release closes that gap. The MCP now exposes the full editing vocabulary over the engine that already exists, in ten tool groups (A–J below): project, media, timeline, transform, effects, colour, text, audio, analysis jobs, and export. Every write is validated against the same strict project schema the editor itself uses before it lands, and every agent mutation is recorded in the project's edit log.

Release note: this page documents the Agent Control surface. The seven original render-lane tools are listed by name in The render lane. If your MCP client lists only those seven, your relay is still on the earlier release and the editing groups have not reached it yet.

Connect

The connection is a personal connect token, issued by the app and scoped to your account. There is no API key and no separate billing anywhere in the flow.

  1. Open the editor and sign in. The token registers under your account, so sign-in comes first.
  2. Open Settings and scroll to the Connections section.
  3. Choose Generate new token. The token starts with clt_. The relay stores only a hash of it, never the token itself.
  4. Add the server to your MCP client with the endpoint and the token as a Bearer header (snippet below).
  5. Ask your agent to list your projects. A working connection answers with your projects and nothing else's.

Endpoint:

https://hjdyvaetxhvxzgsdlibt.supabase.co/functions/v1/cutlab-mcp

Generic MCP client configuration:

{
  "mcpServers": {
    "cutlab": {
      "url": "https://hjdyvaetxhvxzgsdlibt.supabase.co/functions/v1/cutlab-mcp",
      "headers": {
        "Authorization": "Bearer clt_REPLACE_WITH_YOUR_TOKEN"
      }
    }
  }
}

The server speaks stateless MCP over JSON-RPC 2.0 (protocol version 2025-03-26): initialize, tools/list and tools/call, with every call authenticated independently. A plain HTTP smoke test looks like this: 

curl -s -X POST https://hjdyvaetxhvxzgsdlibt.supabase.co/functions/v1/cutlab-mcp \
  -H "Authorization: Bearer clt_REPLACE_WITH_YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}'
# expect: result.serverInfo.name = "cutlab-mcp"

Treat the token like a password. Revoke it in the same Connections section whenever you stop using an assistant; the relay refuses a revoked token from that moment. Background on the token model is in the help page Connect your AI.

The render lane

Editing and rendering are two different jobs, and the MCP keeps them separate. The render lane is how an agent renders a job on its own machine with the CutLab renderer package. Its seven original tools are: list_my_projects, get_project, get_media_links, list_waiting_render_jobs, claim_render_job, complete_render_job and fail_render_job. The flow:

  1. List. list_waiting_render_jobs returns renders queued for your agent (execution lane agent). The CutLab server never touches these.
  2. Claim. claim_render_job takes one job under a one-hour lease and returns the job payload plus signed upload URLs for the finished files. Only the claiming token can complete or fail the job.
  3. Fetch. get_project returns the project JSON; get_media_links returns time-limited download URLs for every input file.
  4. Render. Render locally with the CutLab renderer package, exactly what the job specifies.
  5. Complete. Upload each output to its signed URL, then call complete_render_job. The relay reads the real file sizes back from storage. If anything fails, call fail_render_job with the reason instead of abandoning the job.

Finished renders, on either lane, come back with verification: the probe facts for the file and sampled frame grabs, so the requester can check what actually landed instead of trusting a status flag.

Guardrails

  • Per-account scoping. Every call is authenticated with your connect token. Only its SHA-256 hash is looked up; the account on that row scopes every query. There is no parameter that widens it, and a token only ever sees its own account's projects, jobs and storage.
  • Validated writes. Every agent write is checked against the strict project schema before it lands. An invalid edit is refused, not saved and repaired later.
  • No silent stomping. Writes carry the project's revision. A stale write, based on an older copy than the current one, is refused.
  • Edit log. Every agent mutation is appended to the project's edit log, so agent edits stay inspectable and reversible alongside your own.
  • Media registry discipline. The media registry changes only through the media tools in group B, never as a side effect of a timeline operation.
  • Quotas unchanged. Relay limits are the same for agents as for the app: 50 MB per file and 200 MB per user, enforced in the database and re-checked when a job is claimed.
  • Claim ownership. A claimed render job can only be completed or failed by the token that claimed it, and only while it is running.

Why it is different

Your chat, not your API key. The agent that edits for you is the assistant you already have a conversation with. CutLab never asks for an AI provider's API key and sells no credits; the connect token is the whole arrangement, and you can revoke it at any time.

Web, zero install. The editor runs in any browser and renders on the server or on your agent's machine. A modest computer only ever runs the interface. Originals stay on your machine; the relay moves only the job bundles a render needs.

Verified renders. An agent can check its own work: grab_still shows it a frame before a render is queued, and finished renders return probe facts and frame grabs. Failed renders return structured, stage-level errors instead of a bare failure.

The same vocabulary everywhere. The live control channel that drives the open editor speaks the same operation names as this MCP, so an agent can work on a cloud project or drive the app in front of you without learning a second dialect.

Limits

  • Relay storage quotas: 50 MB per file, 200 MB per user. Originals are not required to live on the relay; they stay on your machine until a job needs them.
  • Delivery formats are MP4 and MOV (H.264 and H.265), the formats CutLab's creators publish in. Pro delivery codecs are deliberately out of scope.
  • Only an assistant that can run code on a machine can take render-lane jobs. A chat that only talks can still edit projects and queue server renders.
